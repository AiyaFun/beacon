## 修掉的五个洞

1. **配额超限让运行悬死在 `running`**。`loop()` 对模型调用没有任何 catch，
   `QuotaExceededError` 抛出后运行没有终态、没有错误、界面转圈到天荒地老，
   而且每次用户打开页面都会触发一次自愈、再撞一次同样的墙。
   现在按 `QuotaExceededError.scope` 分流：
   - **日额度** → 新状态 `waiting_quota`，记下北京时间次日 0 点，到点自动接着跑；
   - **月额度 / 平台预算** → 如实判 `failed`（等一个月的僵尸比失败更糟；平台预算是
     全平台共享的池子，全都挂着等 0 点只会在 0 点一起再烧光一次）。
   catch 刻意放在 `runAgentLoop` **最外层**而不是包住模型调用那一句——会抛错的地方
   不止一处，而「运行必须有个看得见的结局」对所有出错方式都成立。
2. **取消会被后台线复活**。此前每个分支各写各的 `update where id`：用户在模型思考的
   那几十秒里点了终止，这一轮回来照写不误，把 `cancelled` 盖成 `done` / `awaiting_confirm`。
   现在状态只能经 `transition()` 改（带 `from` 条件的 `updateMany` = 乐观锁），
   写落空即安静退出。
3. **取消在轮内不生效**。轮首那道检查只挡得住「上一轮结束前就点了终止」；一轮里可能
   连着调五个工具、每个几十秒到几分钟，用户在中间点终止，剩下的工具照跑照写库。
   现在每次工具执行前复查一次。
4. **封顶数错了东西**。`MAX_STEPS=12` 注释写着「模型轮数」，判的却是步骤流水条数
   （一轮调一次工具就吃掉两条）——写着 12 轮的上限实际约等于 6 次工具调用。
   现在 `rounds` 是独立的一列，`MAX_ROUNDS` 判它；`steps` 保留原义（`AgentStep.seq` 的来源）。
5. **一次执行花了多少钱答不上来**。`LlmCallLog` 加 `runId`。
   ⚠️ **`fn` 保持 `'chat'` 不动**——它不只是记账字段，还是 BYOK 按功能路由的键
   （`gateway.ts` 按 `routing[fn]` 选渠道）。改成 `'agent'` 会让所有只配了 `chat` 路由的
   存量租户静默换渠道，没配默认渠道的直接落 Mock，而 Mock 在执行器里是硬停 `failed`。

## 新增的定时任务：`tick_agent_runs`

`5,15,25,35,45,55 * * * *`（每 10 分钟，与定时智能体错开 5 分钟）。做两件事：
额度重置时刻到了的翻回 `running` 接着跑；租约过期还挂在 `running` 的接手（进程被杀/部署重启）。

**为什么读路径自愈不够了**：此前两种自愈都挂在「用户打开页面看这次运行」上，理由是
「没人看的运行醒不醒都没影响」。执行可以挂起几小时之后这话不成立了——等额度的运行
是在半夜重置的，那时候没有任何人在看页面。

⚠️ cron **必须写成分钟列表**，不能写 `5-59/10`：整机版的本地调度器不认 range-step 语法，
写了那条任务在整机版上永远不跑且没有任何报错。（这次正是 `tests/jobs/local-scheduler.test.ts` 抓到的。）

一次最多处理 20 条：0 点那一下全平台的运行都在等同一个重置时刻，一口气全放出去会
瞬间把新额度再烧光一遍。放不完的下一轮接着放。

## 界面口径

`waiting_quota` 在运行中心归 **`running` 桶而不是 `waiting`**：那一桶的标签写着
「等你处理」，而这里用户什么也做不了、也不用做。到底在等什么由 detail 说清楚
（「今日 AI 额度用完了，北京时间 0 点重置后自动接着跑」）。
助手页徽章同理配灰色不配琥珀色——琥珀色在这套里的意思是「该你动手了」。
终止按钮覆盖这个新状态（不然一次派错的活会挂到 0 点）。

## 守卫

新增 `tests/agent/transition.test.ts`（14 条）+ `tests/runs-center.test.ts` 两条 +
`tests/agent/run.test.ts` 一条（封顶数的是轮数不是流水条数）。
**十一条 mutation 逐条验过会红**：去掉外层 catch / 日额度也判 failed / transition 丢掉 from 条件 /
去掉工具前的状态复查 / 只 kick 不翻状态 / 封顶判据改回 steps / LIVE_STATUSES 去掉新状态 /
waiting_quota 归进等你处理桶 / 运行中心那行直接摆 error / 界面无条件承诺「跑完通知你」/
执行面板把配额原文当红字报错。

其中「只 kick 不翻状态」那条守的是一个反直觉的坑：kick 链路上三道闸
（`claimLease` / `loop` 开头 / `contextForRun`）**全都只认 `running`**，
对一个 `waiting_quota` 的运行踢一脚是**静默无效**的——恰好复刻这一批要修的那个悬死。
所以恢复动作必须先用乐观锁把状态翻回 `running` 再踢。

源码守卫 `lib/agent 下不许绕过 transition 直接写 status` 挡的是明天：
新写一个分支时顺手 `update({ status })` 一次也不会报错，只会在某个并发窗口里
悄悄把用户的终止盖掉。（注意它只看 `data` 段——`where` 里的 status 是读条件，
乐观锁靠的就是它。）
