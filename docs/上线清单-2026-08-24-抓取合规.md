# 上线清单 · 2026-08-24 · 抓取与评论采集合规整改

一轮合规审查后的整改。**没有新功能**，全部是「把已经在做的事说清楚」和「把不该做的做法改掉」。

---

## 一、这轮改了什么，为什么

### 1. 公众号竞对采集：补齐风险告知（🔴 本轮最要紧的一条）

**问题**：这条通道用**用户自己的公众平台登录态**调 `/cgi-bin/searchbiz` 与
`/cgi-bin/appmsgpublish` 两个**非官方**后台接口，查的是**别人的**公众号。
代码里一直知道这件事（`lib/wechat-collect-rules.ts` 文件头写着「踩线的后果由用户自己的号
承担，所以一律往保守取」），商店版 `privacy.md` 第 4 条也如实披露了技术事实——
但**从没告诉过用户后果**，站内服务条款反而把它笼统写成「数据来源于公开信息」，这是失实陈述。
节流规则降低的是概率，不能代替告知。

**改法**（保留功能，补齐告知——用户已确认的方案）：

| 位置 | 改了什么 |
|---|---|
| `extension/sw.js` | `collectWechatOne` 最前面加风险确认闸，**排在节流闸之前**；未确认返回 `code: 'risk_unacked'`，一个请求都不发。带版本号 `WECHAT_RISK_VERSION`，告知内容实质变化时可要求重新确认 |
| `extension/popup.html` / `popup.js` | 首次点「后台采集」弹出就地确认面板，**必须勾选**才能点确认；不确认则功能保持关闭 |
| `extension/options.html` / `options.js` | 设置页新增「公众号竞对采集（默认关，风险自负）」开关，可随时关闭 |
| `app/(public)/legal/terms/page.tsx` | 3.3 重写：数据来源分三类说明，第（三）类逐条讲清非官方接口、可能违反平台协议、后果由用户账号承担、无法代为申诉、节流不能消除风险 |
| 三份隐私政策 | 同上五件事逐条补齐（站内那份此前**整条通道都没提**） |

**闸为什么挂在 `collectWechatOne`**：UI 有三个入口（弹窗、侧栏、网页派下来的任务），
挂在任何一个上都会漏掉另外两个。它是唯一咽喉。
**闸为什么不看 `interactive`**：只拦「用户当场点击」等于定时那轮在从没确认过的情况下照跑。

### 2. 服务端抓取：去伪装 + 遵守 robots（🟠）

**问题**：B 站适配器发的是 `user-agent: Mozilla/5.0` + `referer: https://www.bilibili.com`。
这两个头是「伪装成用户浏览器」的教科书特征，在反不正当竞争诉讼里会被直接当作
「规避技术措施」的证据（淘宝诉美景、微博诉脉脉两案都点过）。而 `lib/web/fetch.ts`
抓任意网页时**完全不看 robots.txt**——robots 在中国不是法律，但百度诉 360 案
（(2013)一中民初字第 2668 号）据此认定违反商业道德、构成不正当竞争。

**改法**：

- `lib/adapters/competitor-real.ts`：B 站改用 `BeaconBot/1.0 (+https://beacon.iyunci.cn)`，去掉伪造 referer。
  **B 站可能因此拒绝请求**——这是可接受的结果，registry 会回退 Mock，用户侧显示为数据源不可用，
  而不是拿一份靠伪装换来的数据。
- 新增 `lib/web/robots.ts`：robots.txt 解析 + 1 小时缓存。`safeFetch` 默认遵守，
  **每一跳重定向都验**（只验起点等于给「用跳转绕开 robots」开门）。
- 新增 `lib/web/ssrf.ts`：SSRF 护栏从 `fetch.ts` 抽出来（robots.ts 也要用它，
  留在原处会成循环 import）。`fetch.ts` re-export 保持既有调用点不变。

**失败时放行还是拦住**：RFC 9309 说 5xx 应视为完全禁止，我们**不这么做**——
4xx（含无 robots.txt）放行是 RFC 语义；5xx / 超时 / DNS 失败放行并记 warn。
把可用性挂在别人服务器的健康度上，代价高于短暂越界。理由写在 `robots.ts` 文件头。

### 3. 评论正文：改准表述 + 开评论者本人的删除入口（🟡）

**问题一**：三份政策都写着「留存下来的是一句句话，**没有任何一条能指向说这句话的人**」。
这句话**在法律上站不住**：剥离九项身份字段后得到的是《个保法》第 73 条的**去标识化**信息，
不是匿名化——评论原文拿回原平台的那条作品下检索仍可能找到发言者。去标识化信息**仍属个人信息**。

**问题二**：`/legal/data-request` 只面向**作品作者**（「确认对所填账号享有相应权利」），
写下评论的**读者本人没有任何入口**，而《个保法》第 27 条（明确拒绝）与第 47 条（删除权）
给的是他本人的权利。

**改法**：

- 三份政策改为准确表述：明说是去标识化、不是匿名化，明说处理依据是第 13 条第 6 项，
  明说靠五条护栏（不采身份字段 + 90 天即删 + 不导出 + 不进语料 + 不做画像）把处理限制在合理范围内。
- `DataRemovalRequest` 加两列 `kind` / `commentText`，表单加「我是评论者本人」一类。

**⚠️ 这里最危险的不是删不掉，是删太多**：评论者填的 handle 是**作品作者**的账号
（他自己的身份我们一个字段都没存，只能靠作品链接定位）。若这条申请混进停采闸，
就成了「张三删掉自己在李四视频下的一条评论」→ 全平台停采李四并删光李四的档案。
因此三道分隔：

1. `isRemovalRequested` 的查询加 `kind: ACCOUNT_KIND`——comment 类永远进不了停采闸；
2. `resolveRemovalRequest` 按 kind 分叉，comment 类只调 `purgeOneComment`，
   返回的 `accounts/posts/watchlistItems/runs` 全是 0；
3. 公开 action 里 comment 类**不做 handle 归一化**——归一之后它在库里就和
   「作者本人要求移除」长得一模一样，只剩 kind 一列拦着。

### 4. 数据来源方披露（🟡）

隐私政策第六节此前只披露了 AI 模型服务商，**没披露竞对/热点数据的来源方**。
新增 6.2 节，逐个列出 YouTube Data API、新榜、TikHub、twitterapi.io、B 站公开接口，
并写明「向它们发出的只有你要查的那个公开账号标识，不含任何身份或内容数据」。

### 5. B 站数据源：改为诚实失败（真机实测的连带发现）

去伪装后**实测发现这条通道根本取不到数据**——而且不是被本次改动弄坏的：

| 请求头 | 结果 |
|---|---|
| `BeaconBot/1.0`（现在） | HTTP 200, `code=-352` 风控校验失败 |
| `Mozilla/5.0` + referer（改动前） | HTTP 200, `code=-403` 访问权限不足 |
| 不带 UA | HTTP 200, `code=-403` |

真因是路径里的 `wbi`——那是 B 站的接口签名机制，URL 必须带 `w_rid`/`wts`，我们从来没算过。
**它此前就是死代码**，只是失败得很安静：

- `fetchPosts` 的 `vlist ?? []` 把失败变成空数组 → registry 判定「真实通道确认这个号没作品」，
  既不熔断、也不回退备源、也不打降级标记；
- `health()` **硬编码 `{ ok: true }`** → 设置页的数据源看板长期对用户说「正常」。

两件加起来，用户看到的是「B 站竞对一条作品都没有」，而不是「这个数据源坏了」。

已修：`assertBiliOk` 让 `code≠0` 抛错触发熔断；`health()` 改为真实探测；
`getJson` 的错误消息带上主机名与状态码（原来只抛一个裸的 `412`，看板上是个孤零零的数字）；
另外四家（TikHub/新榜/YouTube/twitterapi.io）按次计费不宜探连通，
detail 改为明说「只验配置，未探连通」，不再冒充连通性。

**🔒 不要去实现 wbi 签名。** 它**就是** B 站的技术措施本身——本轮刚把伪装 UA 去掉，
理由是「不规避技术措施」，转头破解签名算法是同一件事更重的版本。
守卫在 `tests/adapters/competitor-real-honesty.test.ts`。恢复 B 站数据的正路是商业数据服务商
或官方开放平台；在此之前 B 站竞对靠插件由用户自采（那条路是通的）。

### 6. 政策更新告知：`consentVersion` 不再只写不读

`Member.consentVersion` 从建库起就在**写**（注册、公众号登录、装机向导三处），
却**从来没有一行代码读过它**——隐私政策第九节「重大变更时会通过站内通知或弹窗方式告知」
是一句代码没兑现的承诺。与 `lib/legal/removal.ts` 文件头记的那个缺口同一形状。

新增 `components/LegalUpdateBanner.tsx`，挂在 `TenantShell`（唯一那份外壳）上：
`consentVersion !== LEGAL_VERSION` 时显示横幅，说清这次改了什么，「我知道了」写回新版本。

口径：**横幅不是强制弹窗**。判据是这次改动有没有**扩大处理范围**——
扩大了（新增一类个人信息／新增接收方／扩大用途）该走阻断式单独同意；
没扩大、只是把已在做的事说准确（2026.08.3 就是这种）→ 告知即可。
把「说准确」也做成强制弹窗，会训练用户闭眼点确认，真正需要单独同意那次就没人看了。
`consentVersion` 为空的老用户不打扰（我们不知道他当时看的是哪一版）。

### 7. 新增 `docs/数据源合规留档.md`

逐个数据源记性质、合规评级、待办。**每接一个新数据源，先在这里加一行再写代码**。
依据是《网络数据安全管理条例》第十九条（收集他人数据应具备合法来源）——
向第三方采购不免除责任。

## 五、本轮**没有**做的

- **与 TikHub / twitterapi.io 的数据处理协议**：这两家是第三方逆向接口服务商，
  采购不免除责任。本轮做了披露 + 建了 `docs/数据源合规留档.md` 记下待办，
  但**索取来源合法性承诺、写进合同**这两步是商务动作，得人去做。
- **B 站数据源的替代方案**：现在它诚实地显示为不可用。要恢复 B 站服务端取数，
  需要接持牌数据服务商——本轮没有选型。
- **评论者身份核验**：表单说「可能需要进一步核实」，实际核验仍是人工流程。
- **强制式单独同意**：本轮只做了告知横幅。若将来有真正扩大处理范围的变更，
  需要另做阻断式弹窗（判据见上文第一节第 6 条）。
