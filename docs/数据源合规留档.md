# 外部数据源合规留档

> 建档 2026-08-24（抓取合规审查）。**每接一个新数据源，先在这里加一行再写代码。**
>
> 为什么要这份文件：《网络数据安全管理条例》（2025-01-01 施行）第十九条要求网络数据处理者
> 收集他人数据应当具备**合法来源**。向第三方采购数据不免除责任——如果被认定「明知或应知
> 来源不合法」，采购方一样进链条。而「我们只是买数据」这句话，需要有东西支撑它。
>
> 代码在 `lib/adapters/competitor-real.ts`；对外披露在隐私政策 6.2 节（三份都要同步）。

## 逐条

### YouTube Data API 🟢

平台官方开放接口，有公开的服务条款与配额制度，按 API Key 计费。**这是唯一一个完全没有
灰色地带的数据源**，是其它平台该努力的方向。

- 合规依据：Google API Services User Data Policy + YouTube API Services Terms of Service。
- 待办：无。

### 新榜 NewRank 🟢

国内持牌的第三方内容数据服务商，有工商主体、有公开的商业合作条款。

- 合规依据：与新榜的商业服务合同（**采购时应留存**）。
- 待办：确认合同里有「数据来源合法」的陈述与保证条款。目前没有留档。

### TikHub 🟠 **待补协议**

第三方数据接口服务商，提供抖音 / 小红书的作品数据。这类服务商的数据通常来自对平台
私有接口的逆向，**平台本身并未授权**。

- 风险：若被认定我们「明知或应知」其来源不合法，采购不构成免责事由。
- 待办（按优先级）：
  1. 向对方索取**数据来源合法性的书面承诺**（哪怕只是服务条款里的一句陈述），存档到本目录；
  2. 在服务合同里写入「因数据来源引发的第三方主张由供方负责」的条款；
  3. 若对方无法提供任何合法性说明 → 评估是否改用官方/持牌渠道，或降级为「仅插件自采」。
- **未完成前的处置**：功能保持可用（用户已知悉数据来自第三方，见隐私政策 6.2），
  但不要在营销材料里宣传抖音/小红书竞对数据的完整性与实时性。

### twitterapi.io 🟠 **待补协议**

同 TikHub，性质一致，待办一致。X 官方有 API 但价格高昂，这是绕开它的第三方服务。

### 哔哩哔哩 ❌ **无服务端适配器（2026-09-02 删除）**

曾经的 `BilibiliAdapter` 调 `https://api.bilibili.com/x/space/wbi/arc/search`——B 站 Web 端的**内部接口**，
不是开放平台 API。2026-08-24 真机实测三种 UA 都取不到数据（`code=-352` 风控 / `-403`），
真因是路径里的 `wbi` 签名我们从来没算过，它此前就已经是死代码。

2026-09-02 整个删掉，理由两层：
1. `api.bilibili.com/robots.txt` 是 `Disallow: /`——就算签名问题不存在，服务端直连它也违反本项目自己的
   robots 规矩（`lib/web/robots.ts`），没有给 B 站开例外的理由。
2. **🔒 不要去实现 wbi 签名。** 它**就是** B 站的技术措施本身。去伪装 UA 的理由是「不规避目标站点的
   技术措施」；转头破解签名算法是同一件事更重的版本，而且是主动的、有技术含量的规避。

B 站数据回流只走两条正路：浏览器插件（`extension/content/bilibili.js`，用户自己的浏览器里读公开主页）
与自建 RSSHub 备源（`lib/adapters/rsshub.ts`，无指标）。守卫 `tests/adapters/no-bilibili-server-fetch.test.ts`
钉住「lib/ 与 app/ 不许出现 api.bilibili.com」。

### 浏览器插件 · 读公开页面 🟢

用户在自己的浏览器里，读自己屏幕上已渲染的公开页面。这是"人在浏览"，不是自动化抓取程序。
滚动加载有硬上限（≤12 次 / 30 秒 / 50 条）、定时采集可关闭、每轮有系统通知。

- 合规依据：《个保法》第 13 条第 6 项（合理范围内处理已公开个人信息）+ 用户自身的浏览权限。
- 权利人拒绝的入口：`/legal/data-request`（停采闸在 `lib/legal/removal.ts`，**采集链路真的查它**）。

### 浏览器插件 · 公众号后台 🔴 —— **已于 2026-09-03 整条删除**

曾经用**用户自己的公众平台登录态**调 `/cgi-bin/searchbiz` 与 `/cgi-bin/appmsgpublish`，
查**别人的**公众号；同一条通道还做「每天自动回填我的公众号数据」。它是全项目法律风险最高的一处，
详见 `docs/上线清单-2026-08-24-抓取合规.md` 第一节。

当时做过的缓解：首次使用必须勾选确认风险、设置页可随时关闭、服务条款 3.3 与三份隐私政策逐条告知、
写死的保守节流。但**风险未消除**——它只是从「隐瞒」变成了「知情选择」，而后果（限接口、封功能）
落在用户自己的公众号账号上，我们无法代为申诉。2026-09-03 决定不再靠护栏兜着：整条通道删除，
插件 manifest 不再匹配 `mp.weixin.qq.com` 下的任何页面，`content/wechat-competitor.js` 与
`lib/wechat-collect-rules.ts` 一并删除，三份政策同步撤回该披露（LEGAL_VERSION 2026.09.4）。

公众号**竞对**数据现在只剩两条路：**新榜（持牌商业数据源，服务端取数）** 与
**用户自己导出的文章导入**（`lib/ingest/wechat-export.ts`）。

### 浏览器插件 · 自己的公众号后台 🟡（2026-09-04 按用户要求保留）

与上一条**不是同一件事**，判据是「读的是谁的数据」：这一条只在**用户自己的**后台里读
**用户自己**作品已经渲染出来的数字（阅读/在看/完读率），与视频号/抖音/小红书/B站四个
创作者后台同一条通道、同一套约束（只读、不点击、不调接口、不碰 Cookie、不代替登录）。

比那四个多两道闸：① `mp.weixin.qq.com` **不在 manifest 的安装权限里**，
用户要在设置页单独授权（`chrome.permissions.request`，随时可撤销），没授权一行都不注入；
② 它是**官方发行版专有的可选模块**（`extension/sw-self-backends.js` +
`extension/content/self-backend-wechat.js`），开源发行版按剥离清单去掉。

- 合规依据：用户对自己账号数据的访问权 + 本人登录态下的只读。
- 仍需提醒用户：自动化访问创作者后台是否符合平台约定由用户自行判断，我们只做只读、不代登录。

## 服务端主动抓取的通用规矩

`lib/web/fetch.ts` 的 `safeFetch`（技能导入、群里发链接抓正文）：

- **UA 标识自己**：`BeaconBot/1.0 (+https://beacon.iyunci.cn)`，不伪装浏览器。
- **遵守 robots.txt**：`lib/web/robots.ts`，默认开启，每一跳重定向都验。
  robots 在中国不是法律，但百度诉 360 案（(2013)一中民初字第 2668 号）认定无视它
  违反商业道德、构成不正当竞争。
- **不规避技术措施**：不破解签名、不绕验证码、不模拟登录。
- SSRF 护栏在 `lib/web/ssrf.ts`。

这三条对**插件**不适用——插件是用户本人在自己浏览器里操作，robots 面向的是自动化抓取程序。

## 接新数据源前的自查

1. 它是官方开放接口吗？是 → 🟢，读一遍它的 ToS 就行。
2. 不是的话，是持牌数据服务商吗？是 → 索取来源合法性承诺，存档到本目录。
3. 都不是（自己抓）→ 停下来先问三件事：
   - 抓的是**公开可见**的内容吗？（要登录才能看的一律不行）
   - 用了**任何**规避手段吗？（伪装 UA、破解签名、绕验证码、模拟登录 → 一律不行）
   - 遵守 robots.txt 了吗？
4. 无论哪一类，都要：在隐私政策 6.2 补一行、在本文件补一行、给权利人留移除入口。
