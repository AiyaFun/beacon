# 可观测性（日志 / 错误上报 / 查账 / 告警）

目标是**出事能知道、能查**，不是全套 APM。当前规模刻意不引 pino/OpenTelemetry/Sentry SDK —— 零依赖、零配置可跑，生产能力全部「配置即激活」。

| 能力 | 现状 | 开关 |
| --- | --- | --- |
| 结构化日志 | `lib/logger.ts`，零依赖 | 默认开，`BEACON_LOG_LEVEL` 调级别 |
| 错误上报 | 内置最小 Sentry envelope（fetch 直发） | 配 `BEACON_SENTRY_DSN` 才启用，不配静默跳过 |
| 启动初始化 | `instrumentation.ts`（web）/ `worker.ts`（worker） | 自动 |
| 请求异常捕获 | `instrumentation.ts` 的 `onRequestError` | 自动 |
| 任务/成本账本 | `JobRun` / `LlmCallLog` 两张表（早就有） | 自动 |
| 指标（Prometheus）| **没有**，暂不做 | — |

## 1. 日志

### API

```ts
import { log, createLogger } from '@/lib/logger';

log.info('采集完成', { inserted: 42 });
log.warn('数据源降级', { source: 'weibo' });
log.error('任务失败', { jobName: 'ingest_hot', err });   // error 级会自动上报

// 子 logger：绑定固定字段，后续每条都带上
const l = createLogger({ jobName: 'ingest_hot', tenantId });
l.debug('开始采集');
l.child({ source: 'weibo' }).info('单源完成', { count: 30 });
```

完整导出：

| 导出 | 用途 |
| --- | --- |
| `log` | 根 logger（`debug/info/warn/error/child`）|
| `createLogger(bindings)` | 带固定字段的 logger |
| `redact(value)` | 手动脱敏任意值（返回可安全 `JSON.stringify` 的克隆）|
| `captureException(err, ctx?)` | 手动上报（`log.error` 已自动调，一般用不到）|
| `flushReports(timeoutMs?)` | 进程退出前等在途上报落地 |
| `initObservability(service)` | 启动初始化，进程内调一次 |
| `setReporter(r) / getReporter()` | 换掉内置上报实现（见 §3）|

### 级别

`BEACON_LOG_LEVEL` = `debug` \| `info` \| `warn` \| `error`。不配时：dev=`debug`，prod=`info`。

> 「prod」的判定：`BEACON_ENV=prod` **或** `NODE_ENV=production`。两个都没设也按生产走（宁可少打日志，不可漏密）。

### 格式

- **dev**：带颜色的人类可读行，`err.stack` 单独换行打。
  ```
  08:28:25.133 INFO  采集完成  jobName=ingest_hot tenantId=t_1 inserted=42
  ```
- **prod**：JSON 行，一行一事件，直接喂 Loki / CloudWatch / 阿里云 SLS。
  ```json
  {"level":"info","time":"2026-07-17T08:25:30.883Z","svc":"worker","msg":"任务完成","jobName":"ingest_hot","inserted":42}
  ```

### 字段约定

固定字段由 logger 自己加：`level` / `time` / `svc`(web\|worker) / `msg`。

上下文字段请**复用下面这些名字**，不要另起炉灶（告警和检索都按它们建）：

| 字段 | 含义 |
| --- | --- |
| `tenantId` | 租户 ID，多租户问题排查的第一入口 |
| `workspaceId` / `accountId` | 工作区 / 创作者账号 |
| `requestId` | 请求链路 ID（取 `x-request-id` 头）|
| `jobName` | 任务名，取值同 `lib/jobs/types.ts` 的 `JobName` |
| `jobId` | BullMQ job id |
| `durationMs` | 耗时 |
| `source` | 热榜源 key |
| `provider` / `model` / `fn` | LLM 供应商 / 模型 / 功能路由键 |
| `err` | **Error 对象直接塞这里**，logger 会拆成 name/message/stack 并脱敏 |

## 2. 脱敏（重要）

所有日志输出——包括 `msg` 和全部上下文——都强制过 `redact()`。三层规则：

**① 字段名全打码 `***`**（比较时统一小写、去掉 `_` 和 `-`，所以 `access_key_secret`、`API-KEY`、`apiKey` 等价）：

```
password pwd pass passwd
secret secretkey secretid clientsecret
accesskeyid accesskeysecret
apikey apikeyenc apisecret privatekey
token accesstoken refreshtoken sessiontoken idtoken sessionid session
cookie setcookie authorization auth bearer
masterkey encryptionkey dsn credential credentials signature
smscode verifycode verificationcode otp captcha pin
idcard idnumber bankcard
```

**② 字段名部分保留**（留可辨认片段，方便排查）：

| 字段 | 结果 |
| --- | --- |
| `phone` `mobile` `tel` `phonenumber` `telephone` `contact` | `138****8000`（留前 3 后 4）|
| `email` `mail` `emailaddress` | `w***@gmail.com` |
| `code` | **仅当值像 4-8 位纯数字验证码时**打码。`code: 'ECONNREFUSED'` 保留 |

**③ 值层面兜底**（字段名不敏感也拦，专治上游报错回显密钥）：

| 规则 | 例 |
| --- | --- |
| `sk-` 开头的 key | `sk-abc...` → `sk-***` |
| `Bearer <token>` | → `Bearer ***` |
| 阿里云 / 腾讯云 AccessKey（`LTAI` / `AKID` 前缀）| → `***` |
| URL 里的密码 | `postgresql://beacon:xxx@host/db` → `postgresql://beacon:***@host/db` |

另有防御：递归深度上限 4、数组只留前 20 项、单字符串截断 2000 字符、循环引用标 `[circular]`。

### 已知边界（别踩）

- **字段名叫 `key` 的不打码**。项目里 `key` 绝大多数是平台标识（`{key:'douyin'}`），全打码会让日志没法看。**真密钥请命名为 `apiKey` / `secretKey`**，别叫 `key`。
- 不认识前缀的自定义密钥（既不是 `sk-` 也不在字段名清单里）不会被拦。新增密钥类 env 时，请顺手把字段名加进 `SECRET_KEYS`。
- **不要整包打 `request.headers` 或 `process.env`**。前者有 cookie/authorization（字段名规则能拦），后者字段太杂，靠规则兜不全。
- `lib/sms/provider.ts` 的 Mock 目前直接 `console.log` 验证码。dev 可接受（登录页本来就回显），但**它绕过了 logger，没有脱敏**——生产切真实通道后该分支不会执行，风险可控；建议仍改为 `log.debug` 走 logger（见文末待办）。

## 3. 错误上报

### 默认：内置最小 Sentry envelope

配上 `BEACON_SENTRY_DSN` 即启用，不配就 `reporter=none` 静默跳过。

```bash
BEACON_SENTRY_DSN="https://<publicKey>@o123.ingest.sentry.io/456"
BEACON_RELEASE="v1.2.0"   # 可选，Sentry 里按版本聚合
```

触发时机：
- 任何 `log.error(...)` → 自动上报（`ctx.err` 是 Error 就用它，否则用 msg 合成）
- Next 请求未捕获异常 → `instrumentation.ts` 的 `onRequestError`
- worker 任务失败 / `uncaughtException` / `unhandledRejection`

上报内容：异常 type + message + **原始 stack 文本**（放 `extra.stack`）+ tags（`service` / `tenantId` / `jobName`）+ 脱敏后的上下文。上报体同样过 `redact()`。

保护措施：fetch fire-and-forget、5s 超时、**每分钟最多 60 条**（崩溃循环时不打爆配额）、任何失败都吞掉不影响主流程。DSN 写错只会 warn 一条，不拖垮启动。

### 它给不了什么（诚实说明）

手写的是**最小可用**版本，故意不实现这些：

- ❌ **source map 解析 / stack frame 拆分**——Sentry 里看到的是纯文本 stack，不是可点击的代码行。（这部分手写不靠谱，不如不写）
- ❌ breadcrumbs、performance tracing、release health、session 追踪
- ❌ 前端（浏览器）错误——只覆盖服务端
- ⚠️ 分组（grouping）退化为按 `type + value` 聚合，通常够用，但同名不同源的错误会并到一起

**够用判断**：现阶段要的是「炸了有人知道 + 知道炸在哪个任务/租户」，以上足够。要真正的排障体验（点开就跳到代码行）就该换官方 SDK。

### 升级：换成 @sentry/nextjs

上报层是抽象的（`ErrorReporter` 接口），换实现不用动任何调用点：

1. `npm i @sentry/nextjs`（package.json 有专人负责）
2. 在 `instrumentation.ts` 的 `register()` 里，`initObservability()` **之后**接管：
   ```ts
   const Sentry = await import('@sentry/nextjs');
   Sentry.init({ dsn: process.env.BEACON_SENTRY_DSN, tracesSampleRate: 0.1 });
   const { setReporter } = await import('./lib/logger');
   setReporter({
     name: 'sentry-sdk',
     capture: (err, ctx) => Sentry.captureException(err, { extra: redact(ctx) as Record<string, unknown> }),
     flush: async (ms) => { await Sentry.flush(ms); },
   });
   ```
3. worker 侧同理，在 `worker.ts` 的 `initObservability('worker')` 之后 `setReporter(...)`。
4. 官方 SDK 会自己抓未捕获异常，届时 `log.error` 的自动上报会产生重复——把 `setReporter` 的 `capture` 加个去重或接受重复（Sentry 会按 grouping 合并）。

> **仍然要过 `redact()`**：官方 SDK 不知道我们的敏感字段，直接 `captureException(err, {extra: ctx})` 会把原始 ctx 传上去。

## 4. 查账：JobRun / LlmCallLog

两张表在 `prisma/schema.prisma`，是任务与成本的一手账本。dev 是 SQLite，生产是 Postgres（表名大小写敏感，要加双引号）。

```bash
# dev
npx prisma studio            # 图形界面翻表最快
# 生产
docker compose exec postgres psql -U beacon -d beacon
```

### JobRun（后台任务执行记录）

字段：`name` / `track`(broadcast\|batch_tenant\|event) / `status`(running\|ok\|failed) / `detail` / `tenantId` / `startedAt` / `finishedAt` / `durationMs`。每个任务由 `lib/jobs/handlers.ts` 的 `withRun()` 自动记账。

```sql
-- 最近 24h 各任务成功率（生产 Postgres）
SELECT name,
       count(*) FILTER (WHERE status='ok')     AS ok,
       count(*) FILTER (WHERE status='failed') AS failed,
       round(avg("durationMs")) AS avg_ms
FROM "JobRun"
WHERE "startedAt" > now() - interval '24 hours'
GROUP BY name ORDER BY failed DESC;

-- 最近的失败详情（detail 存了 error.message 前 300 字）
SELECT name, "tenantId", detail, "startedAt"
FROM "JobRun" WHERE status='failed'
ORDER BY "startedAt" DESC LIMIT 20;

-- 卡住的任务：running 超过 30 分钟没收尾（多半是进程被杀，JobRun 没 update 上）
SELECT * FROM "JobRun"
WHERE status='running' AND "startedAt" < now() - interval '30 minutes';
```

### LlmCallLog（LLM 成本账本）

字段：`tenantId` / `fn`(scoring\|generation\|advisor\|compliance\|chat\|embed) / `provider` / `model` / `mocked` / `promptTokens` / `completionTokens` / `costUsd` / `createdAt`。由 `lib/llm/gateway.ts` 的 `recordUsage()` 自动写；`costUsd` 是**估算**，价目表在 `lib/llm/cost.ts`，未知模型走保守默认。

```sql
-- 今日按租户成本排行（单租户单位经济）
SELECT "tenantId", round(sum("costUsd")::numeric, 4) AS usd, count(*) AS calls
FROM "LlmCallLog"
WHERE "createdAt" > current_date AND mocked = false
GROUP BY "tenantId" ORDER BY usd DESC;

-- 按功能拆成本，看哪个环节烧钱
SELECT fn, model, round(sum("costUsd")::numeric, 4) AS usd, sum("promptTokens") AS pt
FROM "LlmCallLog" WHERE "createdAt" > now() - interval '7 days'
GROUP BY fn, model ORDER BY usd DESC;

-- 逐小时成本曲线（查突增）
SELECT date_trunc('hour', "createdAt") AS h, round(sum("costUsd")::numeric, 4) AS usd
FROM "LlmCallLog" WHERE "createdAt" > now() - interval '48 hours'
GROUP BY h ORDER BY h;

-- 降级率：真实 provider 挂了会 fallback 到 mock，mocked=true 突然变多 = 上游有问题
SELECT date_trunc('hour', "createdAt") AS h,
       count(*) FILTER (WHERE mocked) * 1.0 / count(*) AS mock_ratio
FROM "LlmCallLog" WHERE "createdAt" > now() - interval '24 hours'
GROUP BY h ORDER BY h;
```

> SQLite（dev）把 `now() - interval '24 hours'` 换成 `datetime('now','-1 day')`，表名不用引号。

## 5. 建议告警规则

还没有 Prometheus，所以先用**日志关键字告警**（SLS/Loki 都支持）+ **SQL 定时巡检**两种。按重要性排序：

| # | 规则 | 判据 | 数据来源 | 严重度 |
| --- | --- | --- | --- | --- |
| 1 | 健康探针不健康 | 日志 `msg="健康探针不健康"` 出现，或 `/api/health` 非 200 持续 2 分钟 | 日志 / 探针 | P0 |
| 2 | 任务失败 | 日志 `msg="任务失败"` 5 分钟内 ≥ 3 条 | 日志 `svc=worker` | P1 |
| 3 | 任务卡死 | `JobRun` 有 `status='running'` 且 `startedAt` > 30 分钟 | SQL 巡检（每 10 min）| P1 |
| 4 | 任务没跑 | `ingest_hot` 近 90 分钟无 `ok` 记录（正常每 30 min 一次）| SQL 巡检 | P1 |
| 5 | LLM 成本突增 | 单小时 `sum(costUsd)` > 前 7 天同时段均值 × 3，或单日 > 预算阈值 | SQL 巡检（每小时）| P1 |
| 6 | LLM 降级率高 | 单小时 `mocked=true` 占比 > 20%（说明真 provider 在挂，用户拿到的是假数据）| SQL 巡检 | P1 |
| 7 | 短信失败率 | 短信发送失败日志占比 > 10%（**依赖 sms provider 接 logger，见待办**）| 日志 | P1 |
| 8 | 队列积压 | BullMQ `beacon-jobs` waiting > 100 持续 10 分钟（**当前无采集点，见待办**）| Redis | P2 |
| 9 | 未捕获异常 | 日志 `msg="未捕获异常，进程退出"` 出现 | 日志 | P0 |

配了 Sentry 的话，规则 2/9 直接用 Sentry 的 issue alert 更省事。

**阈值都是拍脑袋的起点**，上线后按两周真实数据回调——先松后紧，宁可漏报也别让告警变噪音（没人看的告警等于没有告警）。

## 6. env 清单

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `BEACON_LOG_LEVEL` | dev=`debug` / prod=`info` | 日志级别 |
| `BEACON_SENTRY_DSN` | 空 | 空=不上报。填了才启用 |
| `BEACON_RELEASE` | 空 | 可选，Sentry 版本聚合 |
| `BEACON_HEALTH_TOKEN` | 空 | `/api/health` 详情鉴权，见下 |
| `NO_COLOR` | 空 | 设了就关掉 dev 颜色 |

### `/api/health` 的保护

原来完全公开且把 DB/队列/LLM/数据源状态全吐出去，等于免费给人做内部侦察。现在：

- **公开访问**只回 `{status, ts}` + 状态码（200 ok / 503 degraded）——compose/k8s 探针只看状态码，不受影响。
- **详情**（`checks` 内组件状态）要带 token：
  ```bash
  curl -H "x-beacon-health-token: $BEACON_HEALTH_TOKEN" https://host/api/health
  # 或 Authorization: Bearer <token>
  ```
- **不配 `BEACON_HEALTH_TOKEN`**：dev 直接给详情（零配置可跑）；**prod 一律不给**——避免忘了配 token 就裸奔。所以生产想看详情，就得配。
- token 只认请求头，**不认 query 参数**（token 落进网关/CDN 访问日志就等于泄露），比较用 `timingSafeEqual` 常数时间。
